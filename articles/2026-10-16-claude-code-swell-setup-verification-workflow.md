## はじめに

[前回の記事](https://zenn.dev/tomowingweb/articles/2026-10-09-claude-code-swell-new-project-setup)では、蓄積したSWELL子テーマのREADMEカスタマイズ一覧をコンテキストとして、Claude Codeに新規案件のセットアップファイルを自動生成させる仕組みを構築しました。末尾で予告した通り、今回は**生成された子テーマファイルをMAMPのローカル環境にデプロイし、WordPress管理画面での初期動作確認をClaudeと一緒に行うワークフロー**を紹介します。

前回までの仕組みで「ファイルは生成できた」状態になりましたが、実際にWordPressで有効化してみると「あのフックが効いていない」「管理バーが崩れている」といった問題が出ることがあります。このチェック作業を毎回手動でやると30〜60分かかることもあり、自動化する余地が十分にありました。

今回実装したのは、**Claude Codeを「セットアップ後のペアプログラマー」として使い、チェックリストに基づいた初期動作確認を対話的に進める**ワークフローです。Claudeが何を確認すべきかを整理してくれ、自分はWordPress管理画面を操作しながら結果を報告していく、という流れです。

## 環境

- WordPress 6.x + SWELL子テーマ（GitHub: `tomowingweb/claudecode`）
- MAMP 6.x（macOS ローカル開発環境）
- Claude Code on the Web（手動実行）
- Node.js 20.x / zenn-cli v0.5.x

## 課題：セットアップ後の「最初の動作確認」は意外と手間がかかる

前回の仕組みで生成されたファイル群をMAMPのWordPressに配置すると、次のような確認作業が発生します。

```
初期動作確認（手動でやると毎回発生するチェック項目）:
1. 子テーマの有効化（外観 > テーマ）
2. PHP エラーが出ていないか（wp-config.php の WP_DEBUG で確認）
3. functions.php のインクルードが全て通っているか
4. カスタム投稿タイプが管理画面に表示されているか
5. 管理バーのカスタマイズが効いているか
6. ログイン画面のカスタマイズが表示されているか
7. Contact Form 7 がある場合は確認メールの日本語化が機能するか
8. SWELLカスタマイザーで子テーマ固有の設定が壊れていないか
```

案件ごとに組み込むカスタマイズが変わるため、確認すべき項目も毎回変わります。「今回は Contact Form 7 を入れていないから7は不要」という判断が必要で、これをチェックリストに落とすのが地味に手間でした。

## 実装内容

### 全体ワークフロー

今回のワークフローは「人間がMAMP操作をして、Claudeが進行役を担う対話型」の設計です。

```
Claudeへの初回プロンプト:
「新規案件のセットアップが完了しました。
 生成したファイル一覧: [functions.php, inc/admin-ui.php, inc/cf7-custom.php,
 inc/cpt-works.php, inc/custom-hooks.php, inc/login-custom.php, inc/widgets.php]
 MAMPのWordPressに配置済みです。初期動作確認を一緒に進めてください。」
    │
    ▼
Claudeが「確認チェックリスト」を生成
（生成ファイル一覧から確認すべき項目を自動で判断）
    │
    ▼
対話ループ:
  Claude「ステップ1: 子テーマを有効化してください。完了したら結果を教えてください。」
  人間「有効化しました。管理画面は正常に表示されています。」
  Claude「OK。次はWP_DEBUGで...」
    │
    ▼
全ステップ完了 → 確認結果サマリーをClaudeが生成
    │
    ▼
問題があればその場でコード修正を依頼
（修正 → 再確認のループ）
```

ポイントは**Claudeが生成ファイル一覧から確認項目を動的に生成する**点です。Contact Form 7 のカスタマイズファイルが含まれていれば CF7 の確認ステップが追加され、含まれていなければスキップされます。

### ステップ1：確認チェックリストの自動生成

Claudeへの初回プロンプトを受けて、Claudeはまず以下のようなチェックリストを出力します。

```markdown
## SWELL子テーマ初期動作確認チェックリスト

生成ファイルを分析しました。以下の順序で確認を進めます。

### 基本確認（全案件共通）
- [ ] 子テーマの有効化（外観 > テーマ）
- [ ] WP_DEBUG でPHPエラーなし
- [ ] functions.php のインクルード（wp-includes/general-template.php エラーなし）

### inc/admin-ui.php の確認
- [ ] 管理バーの不要なメニューが非表示になっている
- [ ] 管理画面のフッターテキストがカスタム表示になっている

### inc/login-custom.php の確認
- [ ] ログイン画面のロゴが変更されている
- [ ] ログイン画面のリンク先が正しい

### inc/cpt-works.php の確認
- [ ] 管理メニューに「実績（works）」が表示されている
- [ ] 「実績」の新規投稿画面が正常に表示される

### inc/cf7-custom.php の確認
- [ ] Contact Form 7 プラグインが有効化されている
- [ ] テストメール送信で確認メールが日本語で届く

### inc/widgets.php の確認
- [ ] カスタムウィジェットエリアが外観 > ウィジェット に表示されている

### SWELLカスタマイザー確認
- [ ] 外観 > カスタマイズ が正常に開く（エラーなし）
- [ ] SWELL固有の設定項目が表示されている

確認を始めましょう。まず「子テーマの有効化」から進めてください。
```

このリストはClaudeが生成ファイルの中身を読んで動的に作成します。`inc/cpt-works.php` の中に `register_post_type( 'works', ... )` があるのを読み取って「管理メニューに「実績（works）」が表示されている」という確認項目を生成する、という具合です。

### ステップ2：対話的な確認進行

チェックリストが生成されたあと、確認を一項目ずつ進めていきます。

実際のやり取りの例：

```
人間:「子テーマ有効化しました。ただ管理画面のトップにNoticeが出ています。
      『Child theme is missing the parent theme, SWELL』と表示されています。」

Claude:「このNoticeはSWELLが子テーマの親テーマ認識に失敗している場合に表示されます。
        style.css の Template 行を確認してください。

        確認コマンド:
        cat /Applications/MAMP/htdocs/[案件名]/wp-content/themes/[子テーマ名]/style.css | head -20

        Template: swell になっていますか？ (SWELL の場合テーマディレクトリ名は swell です)」

人間:「Template: Swell になっていました（大文字S）。swell に修正して再読み込みしたらNoticeが消えました。」

Claude:「大文字・小文字の問題でしたね。Linuxサーバーへ本番デプロイ時はこの区別が厳密になるので、
        ローカルで気づけてよかったです。修正内容を functions.php 生成ルールに追加しておきましょうか？
        次回から小文字で生成されるように。」
```

Claudeが「なぜそのエラーが起きるのか」「どこを確認すればいいか」を説明しながら進めてくれるため、WordPress/SWELLの知識が浅い部分でも詰まりにくくなります。

上の例のように、エラーの原因とその場での修正方法を提示したうえで、「次回の自動生成ルールに反映するか？」という改善提案まで行ってくれる点が実用的です。

### ステップ3：問題のフィードバックループ

動作確認中に見つかった問題は、その場でClaudeに修正を依頼できます。

```
人間:「inc/cpt-works.phpのカスタム投稿タイプは表示されているのですが、
      管理画面のメニューアイコンが汎用アイコン（釘のアイコン）になっています。
      dashiconsのポートフォリオアイコン(dashicons-portfolio)にしてほしいです。」

Claude:「inc/cpt-works.php の register_post_type の引数に 'menu_icon' => 'dashicons-portfolio' を
        追加します。」
```

このように、動作確認中に気づいた細かい調整もその場で依頼でき、修正済みファイルが手元に残ります。後で「そういえばアイコン変えたかったんだけど忘れた」とならないのがメリットです。

### ステップ4：確認完了サマリーの生成

全項目の確認が完了すると、Claudeは確認結果のサマリーを生成します。

```markdown
## 初期動作確認 完了サマリー（2026-10-16）

### 確認結果

| チェック項目 | 結果 | 備考 |
|---|---|---|
| 子テーマ有効化 | ✅ 正常 | style.css の Template を小文字に修正 |
| PHPエラー | ✅ なし | WP_DEBUG=true で確認済み |
| 管理バー非表示 | ✅ 正常 | - |
| ログイン画面 | ✅ 正常 | ロゴ・リンク先とも正常 |
| works CPT | ✅ 正常 | アイコンをdashicons-portfolioに変更 |
| CF7確認メール | ✅ 正常 | 日本語で届くことを確認 |
| ウィジェット | ✅ 正常 | - |
| カスタマイザー | ✅ 正常 | SWELLの設定項目表示確認 |

### 今回見つかった問題と修正

1. **style.css の Template ヘッダーが大文字**
   - 修正: `Template: Swell` → `Template: swell`
   - 影響: 子テーマがSWELLの子として認識されないNoticeが出ていた

2. **works CPTのメニューアイコンが未指定**
   - 修正: `register_post_type` に `'menu_icon' => 'dashicons-portfolio'` を追加
   - 影響: 見た目の問題のみ。動作には影響なし

### 今後の自動生成ルールへの追記事項

- style.css の Template ヘッダーは必ず小文字で生成する
- register_post_type にはデフォルトで menu_icon を含める（デフォルト: dashicons-admin-post）

確認は完了です。ローカル環境でのセットアップが正常に動作していることが確認できました。
```

このサマリーには「今後の自動生成ルールへの追記事項」も含まれます。確認中に見つかった問題を次回の自動生成に反映させることで、繰り返し同じ問題で時間を取られることが減ります。

## ポイント

### 「確認項目の動的生成」がペアプログラマーとしてのClaudeの真価

今回のワークフローで最も効果を感じたのは、**Claudeが生成ファイルを読んで確認項目を自動で導き出す**点です。

手動でチェックリストを作ると、「Contact Form 7 を入れていないのにCF7の確認項目が残っていた」「新しく追加したカスタム投稿タイプの確認を忘れた」というミスが起きます。Claudeが毎回ファイルの中身を見て項目を生成するので、この「リストのメンテナンス忘れ」が発生しません。

### WordPressの知識補完としての使い方

SWELLのカスタムフックは公式ドキュメントに掲載されていないものも多く、予期しない挙動に詰まることがあります。そういった場面で「なぜこのエラーが出るのか」「どこを確認すればいいか」をClaudeに聞きながら進められるのは、単純な時間節約以上の価値があります。

特に `style.css` の `Template:` ヘッダーの大文字・小文字問題のように、「ローカル（macOS）では動くがLinuxサーバーでは動かない」というよくある落とし穴も、Claudeが事前に指摘してくれることがあります。

### 修正内容を「自動生成ルール」に即時フィードバック

確認中に見つかった問題をその場で「次回の自動生成ルールに追加するか？」とClaudeが提案してくれる点は、地味に効いてきます。

副業案件を複数並行していると、「前の案件で直したあれ、今回も同じ問題が出た」という繰り返しが起きがちです。確認時の修正が自動生成ルールに即座に反映されることで、同じ問題を2度踏む頻度が減ります。

### 「自分が操作、Claudeが進行役」という分担の快適さ

今回のワークフローでは、実際のMAMP操作（テーマ有効化、管理画面の確認など）は人間が行い、「次は何を確認するか」「どこを見ればいいか」の誘導をClaudeが担います。

この分担は、他の自動化パターン（Claude が全部やる）より実は効率が良いケースがあります。ローカル環境のWordPress管理画面へのアクセスはClaudeには難しく（ブラウザ操作が必要）、かつ実際の動作確認は「目で見て確認する」作業のため、人間の方が向いています。一方で「何を確認すべきか」の整理と「エラー原因の特定」はClaudeの得意領域です。

## まとめ

MAMPのローカル環境でのSWELL子テーマ初期動作確認を、Claude Codeをペアプログラマーとして使って進めるワークフローを構築しました。

| 作業 | 自動化前 | 自動化後（Claude活用） |
|---|---|---|
| 確認チェックリストの作成 | 毎回手動で作成（10〜15分） | 生成ファイルから自動生成（即時） |
| エラー発生時の原因特定 | 自分でドキュメントを調べる（15〜30分） | Claudeがその場で説明（数分） |
| 修正後の再確認 | 確認項目を再度手動チェック（10〜15分） | 修正箇所だけClaudeが誘導（即時） |
| 問題の次回フィードバック | 別途メモを書いておく（忘れがち） | 自動生成ルールへの追記を提案（即時） |

前回から続くシリーズで構築してきた「自動ドキュメント更新 → 新規案件セットアップ自動化 → 初期動作確認支援」のフローが、ここで一段落します。

各ステップが前のステップの成果物（READMEカスタマイズ一覧、生成されたPHPファイル）を引き継いで動くため、シリーズ全体として「蓄積が増えるほど効率が上がる」正のフィードバックが働く設計になっています。

次回は、ローカルで動作確認が取れた子テーマを**本番のレンタルサーバーへデプロイする手順をClaudeと一緒に進める**実践例を予定しています。FTP/SFTPでのデプロイからWordPressダッシュボードでの有効化まで、本番特有の注意点（パーミッション、php.iniの違いなど）を含めてまとめます。
