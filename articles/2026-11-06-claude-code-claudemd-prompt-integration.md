## はじめに

[前回の記事](https://zenn.dev/tomowingweb/articles/2026-10-30-claude-code-swell-prompt-templates)では、副業のWordPress/SWELL案件で使える**場面別プロンプトテンプレート集**を紹介しました。

テンプレートを用意しただけでは、毎回「どのテンプレートを使うか探す」「プロジェクト固有の変数（関数名プレフィックスやPHPバージョンなど）を埋める」という作業が発生します。セッションのたびに同じコンテキストをClaudeに伝え直すのは、積み重なると意外と大きな手間です。

本記事では、**CLAUDE.mdにプロンプトテンプレート集への参照と案件固有変数を持たせることで、セッション開始直後からClaudeが「このプロジェクトの文脈を理解した状態」で動ける**ようにする仕組みを紹介します。

## 環境

- WordPress 6.x + SWELL子テーマ（GitHub: `tomowingweb/claudecode`）
- MAMP 6.x（ローカル開発環境）
- レンタルサーバー：エックスサーバー
- Claude Code on the Web（自動実行 + 手動実行）

## 実装内容

### リポジトリ構成の変更

前回記事の「テンプレートはバージョン管理する」の提案を実際に実装しました。リポジトリのルートに `prompts/` ディレクトリを新設し、CLAUDE.mdからリンクを貼る構成にします。

```
claudecode/
├── prompts/
│   ├── 01-setup.md        # セットアップ時のプロンプト
│   ├── 02-debug.md        # デバッグ時のプロンプト
│   ├── 03-customize.md    # カスタマイズ時のプロンプト
│   └── 04-handover.md     # 引き継ぎ時のプロンプト
├── inc/
│   ├── admin-ui.php
│   ├── login-custom.php
│   └── ...
├── CLAUDE.md
├── functions.php
└── style.css
```

### CLAUDE.mdの全体構成

CLAUDE.mdには以下の5セクションを設けます。

```markdown
# CLAUDE.md — SWELL子テーマ開発プロジェクト

## 1. プロジェクト概要
## 2. コーディング規約（Claudeへの制約）
## 3. 案件固有の変数（毎回変えずに済む共通情報）
## 4. プロンプトテンプレートへの参照
## 5. 注意事項・やってはいけないこと
```

各セクションの詳細を以下で説明します。

---

### セクション1：プロジェクト概要

```markdown
## 1. プロジェクト概要

このリポジトリは WordPress テーマ SWELL の子テーマです。
副業のWeb制作案件で使用しています。

- 親テーマ: SWELL（有料テーマ、このリポジトリには含まれない）
- ローカル環境: MAMP（macOS）
- 本番環境: エックスサーバー（PHP 8.2）
- バージョン管理: GitHub（プライベートリポジトリ）

**セッション開始時にClaudeが最初にすること：**
1. `git log --oneline -5` で直近のコミットを確認する
2. `README.md` のカスタマイズ一覧を確認する
3. 作業依頼の内容に応じて `prompts/` の該当ファイルを参照する
```

**ポイント：「セッション開始時にClaudeが最初にすること」を明記する**

CLAUDE.mdはセッション開始時にClaudeに自動的に読み込まれます。ここに「最初にすること」を書いておくことで、毎回「前回何をやっていたか確認してください」と依頼しなくても、Claudeが自動でプロジェクトの状態を把握します。

---

### セクション2：コーディング規約

```markdown
## 2. コーディング規約

### PHP
- 関数名プレフィックス: `wingweb_` を必ず使う（例: `wingweb_custom_login_logo()`）
- インデント: タブ（スペース不可）
- PHP 8.1以上を前提としたコードのみ（短縮三項演算子 `?:` を使っても良いが、`match` 式は PHP 8.0以上が必要なので注意）
- `get_stylesheet_directory()` でパスを解決する（絶対パスのハードコード禁止）
- 全ての関数に `add_action` / `add_filter` のフックを明記する

### ファイル追加・変更のルール
- `functions.php` には `require_once` による読み込みのみ書く（ロジックは書かない）
- 機能別に `inc/` ディレクトリにファイルを分ける
- 新ファイルを追加したら `README.md` のカスタマイズ一覧を必ず更新する

### コミットメッセージ
- `feat:` 新機能追加
- `fix:` バグ修正
- `docs:` ドキュメントのみの変更
- `refactor:` 動作を変えないリファクタリング
```

### セクション3：案件固有の変数

ここが今回の仕組みの核心です。前回のプロンプトテンプレートでは `[角括弧]` で示していた変数を、CLAUDE.mdに定数として定義します。

```markdown
## 3. 案件固有の変数（このプロジェクトの固定値）

Claudeへ：以下の値を、プロンプトテンプレートの `[角括弧]` 変数の代わりに使ってください。

| 変数名 | 値 |
|---|---|
| `[案件スラッグ]` | `wingweb` |
| `[関数名プレフィックス]` | `wingweb_` |
| `[PHPバージョン（ローカル）]` | `8.2`（MAMP） |
| `[PHPバージョン（本番）]` | `8.2`（エックスサーバー） |
| `[WordPressバージョン]` | `6.7.x` |
| `[SWELLバージョン]` | `最新安定版（確認は管理画面で）` |
| `[本番サーバー]` | `エックスサーバー` |
| `[子テーマのTheme Name]` | `SWELL Child by wingweb` |
| `[style.cssのTemplate値]` | `swell`（必ず小文字） |
```

この定義があることで、Claudeはプロンプトテンプレートの変数を自動的に埋めることができます。「子テーマの初期ファイルを生成してください」と依頼するだけで、`wingweb_` プレフィックスの関数名、`PHP 8.2` 互換のコードが生成されます。

### セクション4：プロンプトテンプレートへの参照

```markdown
## 4. プロンプトテンプレートへの参照

各作業の場面に応じて、以下のテンプレートファイルを参照してください。

| 作業場面 | 参照ファイル |
|---|---|
| 新規案件セットアップ（子テーマ初期ファイル生成） | `prompts/01-setup.md` |
| デバッグ・動作確認・デプロイ前レビュー | `prompts/02-debug.md` |
| 機能追加・カスタマイズ（CPT追加、CF7設定など） | `prompts/03-customize.md` |
| 引き継ぎドキュメント・README更新 | `prompts/04-handover.md` |

**使い方：**
1. ユーザーから「〇〇してください」と依頼が来たら、上記の対応するテンプレートファイルを読む
2. `[角括弧]` の変数を「セクション3：案件固有の変数」の値で置き換える
3. 追加情報が必要な場合のみユーザーに確認する
```

### セクション5：注意事項

```markdown
## 5. 注意事項・やってはいけないこと

### 絶対にやってはいけないこと
- `functions.php` にロジックを直接書く（`inc/` に分離すること）
- `style.css` の `Template:` フィールドに大文字を使う（`swell` と小文字で書くこと）
- 絶対パスをハードコードする（`/Applications/MAMP/...` などのローカルパスを含めないこと）
- `published: true` の Zenn 記事ファイルを変更する（Zennへの公開は手動で行う）

### 本番デプロイ前に必ず確認すること
- `WP_DEBUG = false` の環境でNotice/Warningが出ないこと
- エックスサーバーのPHPバージョンとの互換性
- SWELLのフックがバージョン間で変わっていないこと（リリースノートを確認）

### Zennリポジトリとの兼務について
このセッションは `tomowingweb/zenn-articles` にもアクセスできます。
Zenn記事の自動生成ジョブが定期実行されます。記事の `published:` フラグは必ず `false` のまま残し、公開操作は行わないでください。
```

### CLAUDE.mdを機能させるための `prompts/` ファイル整備

CLAUDE.mdからの参照先となるテンプレートファイルも整備します。例として `prompts/01-setup.md` の冒頭を示します。

```markdown
# セットアップ時のプロンプトテンプレート

## テンプレート1-A：子テーマ初期ファイルの生成

> **使用前の確認：** CLAUDE.mdの「案件固有の変数」セクションで変数を確認してください。

以下の要件でSWELL子テーマの初期ファイルを生成してください。

【案件概要】
- サイト種別: [コーポレートサイト / ポートフォリオ / ランディングページ]
- クライアント業種: [業種]
- 必要な機能:
  - [カスタム投稿タイプ（例: 実績・news・staff）]
  - [お問い合わせフォーム（Contact Form 7）]

【生成ファイル一覧】
...（以下、前回記事のテンプレートと同じ）
```

各テンプレートファイルの冒頭に「使用前の確認：CLAUDE.mdを参照」と書くことで、Claudeが変数を参照するフローが確立します。

## ポイント

### CLAUDE.mdは「Claudeへの仕様書」として書く

通常のREADMEは「人間が読む」ことを前提にしますが、CLAUDE.mdは「Claudeが読んで動くための仕様書」です。この違いを意識することで、より実用的なCLAUDE.mdが作れます。

具体的には、**命令形で書く**ことを意識します。「〇〇である」ではなく「〇〇にすること」「〇〇した後は〇〇を確認すること」という書き方です。Claudeは宣言的な文章よりも指示的な文章に従いやすい傾向があります。

### 変数の定義で「埋め合わせコスト」が消える

前回のプロンプトテンプレートの `[角括弧]` 変数が、毎回のコスト源でした。「このプロジェクトの関数名プレフィックスは `wingweb_` です」と毎回プロンプトに書く手間は小さいようで、週に複数回セッションを開くと積み重なります。

CLAUDE.mdで一度定義すれば、以降は「CPTを追加してください」と依頼するだけで、`wingweb_register_cpt_works()` のような関数名が自動的に使われます。

### 「Claudeが最初にすること」を明記するとオリエンテーションが不要になる

以前は毎回セッション冒頭で「前回のコミットを確認してください。README.mdも確認してください」という依頼を手動で行っていました。CLAUDE.mdに「セッション開始時にClaudeが最初にすること」を書いておくことで、このオリエンテーション作業がなくなります。

セッション開始直後から「直近5件のコミットを確認しました。今回の変更はXXXですね」という状態でやりとりできるようになります。

### CLAUDE.mdを変更したらコミットする習慣をつける

CLAUDE.mdはプロジェクトのナレッジベースです。案件をこなすたびに「このケースでは〇〇を制約に加えると良かった」という知見が生まれます。その都度CLAUDE.mdを更新してコミットする習慣をつけると、次の類似案件でその知見が活きます。

更新のタイミングは以下が目安です：

- 新しいカスタマイズパターンを初めて実装したとき
- 本番デプロイで問題が起きて回避策を発見したとき
- SWELLやWordPressのバージョンアップで動作が変わったとき
- 引き継ぎ先のエンジニアから「この情報が足りなかった」と言われたとき

## まとめ

CLAUDE.mdとプロンプトテンプレートを統合した結果、セッションの開始フローが以下のように変わりました。

**Before（CLAUDE.md整備前）：**
1. Claude Codeを開く
2. 「このプロジェクトはSWELL子テーマです。関数名プレフィックスはwingweb_で、PHPは8.2を前提にしてください」と説明する
3. 「直近のコミットを確認してください」と依頼する
4. 「README.mdを確認してください」と依頼する
5. 「今回は〇〇をお願いします。テンプレートはZenn記事のxx番目です」と依頼する
6. テンプレートの変数を手動で指定する

**After（CLAUDE.md整備後）：**
1. Claude Codeを開く
2. 「今回は〇〇をお願いします」と依頼する

ステップ2〜6が省略され、プロジェクトの立ち上がりが体感的に速くなりました。毎回「SWELL子テーマです」と説明しなくて済むという単純な変化でも、週に複数回セッションを開く副業では大きな差になります。

次回は、このCLAUDE.mdとプロンプトテンプレートの仕組みを**新規案件に横展開する方法**を紹介します。今回作ったCLAUDE.mdのベースをテンプレートリポジトリ化し、新規案件セットアップ時にテンプレートから生成してプロジェクト固有の変数だけを書き換えるフローです。
