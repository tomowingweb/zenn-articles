## はじめに

[前回の記事](https://zenn.dev/tomowingweb/articles/2026-10-16-claude-code-swell-setup-verification-workflow)では、SWELL子テーマをMAMPのローカル環境に配置し、Claude Codeをペアプログラマーとして動作確認を進めるワークフローを紹介しました。ローカルでの動作確認が完了し、いよいよ本番環境へデプロイする段階です。

本番デプロイは、ローカル作業と比べて注意点が格段に増えます。FTP/SFTPの接続設定、ファイルのパーミッション、本番のphp.iniとローカルの差異、WordPressのデバッグモードの扱いなど、うっかりミスが起きやすい場面が続きます。「ローカルでは動いていたのに本番でエラーが出た」経験は、WordPress案件を複数こなしていれば一度や二度は通る道です。

今回は、**ローカルで検証済みのSWELL子テーマを本番のレンタルサーバーへデプロイする一連の作業を、Claude Codeをナビゲーターとして進めるワークフロー**を共有します。FTP設定の確認からWordPressダッシュボードでの有効化まで、Claude Codeが「次に何をすべきか」「どこに落とし穴があるか」を案内してくれる流れです。

## 環境

- WordPress 6.x + SWELL子テーマ（GitHub: `tomowingweb/claudecode`）
- MAMP 6.x（ローカル開発環境）
- レンタルサーバー：エックスサーバー（PHP 8.1系）
- FTPクライアント：FileZilla
- Claude Code on the Web（手動実行）

## 課題：本番デプロイは「ローカルと本番の差」を意識しないとはまる

ローカル（MAMP）と本番（レンタルサーバー）の間には、いくつかの重要な違いがあります。

```
ローカル（MAMP）と本番（エックスサーバー）の主な差異:

1. PHPバージョン
   MAMP: PHP 8.2.x（最新を使いがち）
   エックスサーバー: PHP 8.1.x（設定で変更可だが、デフォルトはやや古い）

2. WP_DEBUG の扱い
   ローカル: WP_DEBUG=true にして開発（エラーが画面に出る）
   本番: WP_DEBUG=false が必須（エラーが画面に出ると情報漏洩リスク）

3. ファイルパーミッション
   ローカル: パーミッション緩め（644/755でだいたい動く）
   本番: サーバーによってはPHPファイルに実行権限が不要/不可

4. メモリリミット
   ローカル: php.iniで自由に設定できる
   本番: プランによって上限がある（128MB〜256MB程度）

5. functions.php のパス解決
   ローカル: MAMP独自のパス（/Applications/MAMP/...）
   本番: サーバーの絶対パス（/home/.../public_html/...）
```

これらの差異を意識せずにデプロイすると、「ローカルでは動くが本番では動かない」が発生します。

## 実装内容

### デプロイ前チェックリストの自動生成

デプロイ作業の開始前に、Claudeに「デプロイ前チェックリスト」を生成させます。前回の動作確認ワークフローと同じ発想で、Claudeがコードを読んで本番特有のリスクを先に洗い出します。

```
Claudeへのプロンプト:
「SWELL子テーマのローカル動作確認が完了しました。
 本番（エックスサーバー）へのデプロイを進めます。
 生成ファイル一覧: [functions.php, inc/admin-ui.php, inc/cf7-custom.php,
 inc/cpt-works.php, inc/custom-hooks.php, inc/login-custom.php, inc/widgets.php]
 デプロイ前に確認すべきことを洗い出してください。」
```

Claudeからは次のようなチェックリストが出力されます。

```markdown
## デプロイ前チェックリスト

### コード側の確認（デプロイ前に修正が必要な場合あり）

- [ ] WP_DEBUG が false になっているか（wp-config.php を確認）
      → ローカル開発中は true にしていることが多い。本番は必ず false に。

- [ ] __DIR__ や dirname(__FILE__) の使用箇所を確認
      → MAMP固有の絶対パスをハードコードしていないか。
      → functions.phpやincファイルでの `require_once` の書き方を確認。

- [ ] PHPバージョン互換性の確認
      → ローカルがPHP8.2で本番が8.1の場合、8.2で追加されたsyntax（Readonly Properties等）を
         使用していると本番でエラーになる。

- [ ] CF7確認メール送信設定のメールアドレス
      → cf7-custom.php に直書きしているメールアドレスが、本番サーバーと合っているか確認。

### サーバー側の事前確認

- [ ] エックスサーバーのPHPバージョン設定
      → サーバーパネル > PHP Ver.切替 でローカルと合わせるか、差異を把握する。

- [ ] FTP接続情報の確認（ホスト/ユーザー/パスワード）
      → デプロイ先ディレクトリのパス（wp-content/themes/[子テーマ名]/）を事前に確認。

- [ ] 既存テーマのバックアップ
      → 本番に同名ディレクトリが存在する場合（更新デプロイ時）、FTPでダウンロードしてバックアップ。
```

ローカルのコードを実際に読んで「このファイルには `__DIR__` を使っているか」「CF7設定に固有のメールアドレスが直書きされているか」を確認した上でリストを作成してくれます。汎用的なチェックリストではなく、自分のコードに特化した指摘が出てくる点が助かります。

### WP_DEBUGの切り替え確認

Claudeが指摘したポイントの一つ目は WP_DEBUG の確認です。

```
Claude:「wp-config.php を確認してください。
        `define('WP_DEBUG', true);` と記述されている場合は
        `define('WP_DEBUG', false);` に変更してからデプロイしてください。
        本番でWP_DEBUGがtrueのままだと、PHPの警告やエラーがWebページに
        そのまま表示され、セキュリティ上の問題になります。」
```

これはうっかりやりがちなミスのひとつです。ローカルでデバッグしながら開発しているとtrueのままになっており、本番に持っていってもそのままになっているケースが実際にありました。

### PHPバージョン互換性チェック

本番のPHPバージョンがローカルと異なる場合の確認です。

```
人間:「エックスサーバーのPHPバージョンを確認したところ、8.1.29でした。
      ローカルのMAMPはPHP8.2.10です。」

Claude:「PHP 8.1と8.2の間で注意が必要な変更点を確認します。
        生成ファイルを見たところ、`readonly` プロパティや
        `enum` は使用されていないため、基本的に互換性の問題はなさそうです。

        念のため、以下のsyntaxが含まれていないか確認してください：
        - `readonly class`（8.2追加）
        - `Disjunctive Normal Form (DNF) Types`（8.2追加）
        - `true` を単独のtypeとして使用（8.2追加）

        確認コマンド:
        grep -rn 'readonly class\|true $\|true|' inc/ functions.php」
```

grepコマンドを提示してくれるので、そのままターミナルで実行して確認できます。

### FTPデプロイの実施

チェックリストの確認が完了したら、FileZillaでのデプロイに移ります。

```
人間:「チェックリストの確認が完了しました。WP_DEBUGはfalseに変更しました。
      PHPバージョン互換性の問題もありませんでした。
      これからFileZillaでデプロイします。」

Claude:「了解です。デプロイの手順を確認します。

        1. FileZillaでエックスサーバーに接続
           ホスト: [ドメイン名]
           ユーザー: [FTPユーザー名]
           ポート: 21（FTP）または 22（SFTP、使える場合はSFTPを推奨）

        2. デプロイ先ディレクトリを開く
           /home/[アカウント名]/[ドメイン名]/public_html/wp-content/themes/

        3. 同名ディレクトリが存在する場合（更新時）
           → 先にダウンロードしてバックアップしてから上書き
           → 既存ディレクトリの削除・再作成より上書きの方が安全

        4. ローカルのSWELL子テーマディレクトリをアップロード
           アップロード対象: wp-content/themes/[子テーマ名]/

        アップロード完了したら報告してください。
        ファイル数が多い場合は完了まで数分かかることがあります。」
```

SFTPを推奨している点が地味に重要です。FTPは通信が暗号化されないため、本番サーバーへのデプロイにはSFTPを使うべきです。毎回これを意識できるかは怪しく、Claudeが「SFTPを推奨」と一言言ってくれることで習慣になります。

### 本番WordPress管理画面での有効化と確認

デプロイ完了後、本番のWordPress管理画面での確認に移ります。

```
人間:「FileZillaでのアップロードが完了しました。」

Claude:「お疲れ様です。本番の管理画面での有効化と確認を進めましょう。

        【確認手順】

        1. WordPress管理画面にログイン
           URL: https://[ドメイン名]/wp-admin/

        2. 外観 > テーマ を開く
           アップロードした子テーマが表示されているか確認。
           表示されていない場合 → ディレクトリ名のスペルを確認（大文字・小文字も）

        3. 子テーマを有効化
           「有効化」ボタンをクリック

        4. 有効化後にPHPエラーが出ていないか確認
           画面に「Fatal error:」「Warning:」が表示されていないか確認。
           表示されている場合 → エラーメッセージを教えてください。

        5. サイトのトップページをブラウザで開く
           管理画面のエラーがなくても、フロントエンドにエラーが出る場合あり。
           Chromeの開発者ツール(F12) > Consoleでエラーが出ていないか確認。」
```

ローカルとまったく同じ手順ですが、本番では「エラーが出た時の確認場所」が少し異なります（ローカルはWP_DEBUG=trueでスクリーンに出るが、本番はfalseのため画面には出ない）。Claudeはこの違いを踏まえた確認手順を案内してくれます。

### 本番特有の問題と対処例

実際にデプロイして発生した問題の例を紹介します。

**問題1: functions.phpのインクルードパス**

```
人間:「テーマを有効化したところ、フロントページが白くなりました。
      wp-config.php の WP_DEBUG を一時的にtrueにして確認したところ、
      Fatal error: require_once(/Applications/MAMP/htdocs/...): 
      Failed to open stream: No such file or directory と表示されました。」

Claude:「MAMP固有のパスがハードコードされているようです。
        functions.php でインクルードしているパスを確認してください。

        問題のある書き方（絶対パスをハードコード）:
        require_once '/Applications/MAMP/htdocs/corp2026/wp-content/themes/corp2026-child/inc/admin-ui.php';

        正しい書き方（テーマのディレクトリから相対解決）:
        require_once get_stylesheet_directory() . '/inc/admin-ui.php';

        get_stylesheet_directory() はWordPressの関数で、有効化された子テーマの
        ディレクトリパスを返します。ローカル・本番どちらでも正しいパスが使われます。」
```

これは実際にやったことがあるミスです。ローカル開発中に「とりあえず動かしたい」とフルパスで書いてしまい、本番に持ってきて初めて気づく。`get_stylesheet_directory()` を使うのが正しいのは知識としては知っていても、コードレビューがないと見落としがちです。

**問題2: メモリリミット**

```
人間:「管理画面のカスタマイザーを開くと、しばらくしてから
      「Fatal error: Allowed memory size of 134217728 bytes exhausted」
      が出ます。ローカルでは問題ありませんでした。」

Claude:「メモリリミット（128MB = 134217728 bytes）の上限に達しています。
        エックスサーバーはデフォルトで128MBのことが多いです。

        対処方法（優先順）:

        1. wp-config.php で増量を試みる:
           define('WP_MEMORY_LIMIT', '256M');
           ただしサーバーの上限を超えては増量できません。

        2. functions.php でも試みる（wp-config.phpより後から読まれる場合の代替）:
           ini_set('memory_limit', '256M');
           
        3. エックスサーバーのサーバーパネルでPHPのメモリ上限設定を確認・変更する
           パス: PHP設定 > php.ini の設定 > memory_limit

        まずサーバーパネルで memory_limit の現在値を確認してください。」
```

ローカルのMAMPはphp.iniで自由にメモリを増やせますが、本番サーバーには上限があります。この問題もデプロイしてみて初めて気づくケースが多く、Claudeが先回りして確認を促してくれると時間の節約になります。

## ポイント

### 「ローカルと本番の差」をデプロイ前に洗い出すことが最大の節約

今回のワークフローで最も効果があったのは、**デプロイ前のチェックリスト生成**です。

WP_DEBUG、パス解決、PHPバージョン互換性——これらはデプロイしてみるまで問題が分からないことが多く、エラーが出てから原因を調査するのに時間がかかります。Claudeがコードを読んで「このコードには本番でリスクになりうる箇所がある」と事前に指摘することで、デプロイ後の問題解決時間が大幅に減りました。

### SFTPの習慣化

FileZillaの設定でFTPとSFTPのどちらを使うかは、意外と無頓着になりがちです。Claudeが毎回「SFTPを推奨」と案内することで、セキュアな接続が自然と習慣になります。副業でクライアントのサーバーに接続する場合、FTPとSFTPの違いを意識することは特に重要です。

### 本番デプロイを「可逆的な作業」にするバックアップの徹底

上書きデプロイを行う場合の「先にバックアップ」という手順も、Claudeが毎回案内します。バックアップなしで上書きして問題が起きると、元に戻す手段がなくなります。「一応バックアップ取っておきましょう」という一言があるかどうかで、後悔するケースを防げます。

### エラーが起きた時の調査手順が効率化される

本番でエラーが出た場合、ローカルとは確認方法が異なります（WP_DEBUGの一時的な有効化、エラーログの場所など）。Claudeがこの手順を案内することで、「どうやってエラーの内容を確認するか」から考え始めなくて済みます。

エックスサーバーの場合、エラーログは `~/[ドメイン名]/logs/php_errors.log` にあることが多く、Claudeはこの場所も案内してくれます。

## まとめ

ローカルで動作確認済みのSWELL子テーマを、Claude Codeをナビゲーターとして本番レンタルサーバーへデプロイするワークフローを構築しました。

| 作業 | Claude活用前 | Claude活用後 |
|---|---|---|
| デプロイ前チェック | 経験則で思い出した項目のみ確認 | コードを読んだ上での網羅的なリスク洗い出し |
| WP_DEBUGの確認 | 忘れることあり | デプロイ前チェックで必ず指摘される |
| パス解決の問題 | デプロイ後にエラーで気づく | デプロイ前にコードを読んで検出 |
| エラー発生時の調査 | ドキュメントを自分で調べる | Claudeが確認手順と対処法を即時案内 |
| SFTPの徹底 | 忘れることあり | 毎回推奨される |

今回で、「自動ドキュメント更新 → 新規案件セットアップ自動化 → 初期動作確認支援 → 本番デプロイ支援」という4ステップのシリーズが完結しました。

このシリーズを通じて、副業のWordPress/SWELL案件における反復作業の多くをClaude Codeと分担できるようになりました。Claudeが「何をすべきか」「どこに落とし穴があるか」を案内し、人間が実際の操作を担う分担は、AIが全部やる自動化よりも現実的で、かつ品質の担保もしやすいバランスです。

次回は、今回のシリーズで蓄積したノウハウを整理し、**副業WordPress案件でClaude Codeを活用する際の実践的なプロンプトテンプレート集**をまとめる予定です。プロンプトの書き方次第でClaudeの出力品質が大きく変わる経験を踏まえ、各場面で実際に使っているプロンプトを共有します。
