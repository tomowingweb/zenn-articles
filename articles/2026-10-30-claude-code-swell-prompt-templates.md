## はじめに

[前回の記事](https://zenn.dev/tomowingweb/articles/2026-10-23-claude-code-swell-deploy-rental-server)で、「自動ドキュメント更新 → 新規案件セットアップ自動化 → 初期動作確認支援 → 本番デプロイ支援」という4ステップのシリーズが完結しました。このシリーズを通じて痛感したのが、**Claude Codeへのプロンプトの書き方が出力品質を左右する**という事実です。

同じ作業を依頼するにしても、プロンプトの書き方次第でClaudeの出力がまるで変わります。「SWELLのfunctions.phpを修正して」と曖昧に頼むより、「以下の要件を満たすSWELL子テーマのfunctions.phpを生成してください。既存のコードは変更せず追記のみで対応してください」と具体的に書いた方が、期待に近い出力が得られます。

本記事では、**副業のWordPress/SWELL案件で実際に使っているプロンプトテンプレート**を場面別にまとめます。コピー＆ペーストして使えるよう、変数部分を `[角括弧]` で示しています。

## 環境

- WordPress 6.x + SWELL子テーマ（GitHub: `tomowingweb/claudecode`）
- MAMP 6.x（ローカル開発環境）
- レンタルサーバー：エックスサーバー
- Claude Code on the Web（手動実行）

## 実装内容

### カテゴリ1：新規案件セットアップ

#### テンプレート1-A：子テーマ初期ファイルの生成

案件の要件定義から子テーマの初期ファイルを一括生成する場面のプロンプトです。

```
以下の要件でSWELL子テーマの初期ファイルを生成してください。

【案件概要】
- サイト種別: [コーポレートサイト / ポートフォリオ / ランディングページ]
- クライアント業種: [業種]
- 必要な機能:
  - [カスタム投稿タイプ（例: 実績・news・staff）]
  - [お問い合わせフォーム（Contact Form 7）]
  - [その他の機能]

【生成ファイル一覧】
- functions.php（インクルードのみ、ロジックはincに分離）
- inc/admin-ui.php（管理バーカスタマイズ、フッターテキスト変更）
- inc/login-custom.php（ログイン画面カスタマイズ）
- inc/cpt-[投稿タイプ名].php（カスタム投稿タイプ定義）
- inc/cf7-custom.php（CF7確認メール日本語化）
- inc/custom-hooks.php（SWELLカスタムフック）
- style.css（子テーマ宣言のみ）

【制約】
- PHPのバージョン互換性: PHP 8.1以上
- get_stylesheet_directory() でパスを解決する（絶対パスのハードコード禁止）
- WP_DEBUG=trueの環境でNoticeが出ないコードにする
- 関数名のプレフィックス: [案件スラッグ]_
```

このテンプレートで重要なのは「制約」のセクションです。PHP 8.1互換性や `get_stylesheet_directory()` の指定は、後で本番デプロイ時にはまるポイントを事前に防ぐための記述です。これを書かずに生成させると、MAMPのローカルパスがハードコードされたコードが出てくることがあります。

#### テンプレート1-B：style.cssヘッダー確認

```
生成した style.css の子テーマヘッダーを確認してください。
特に以下の点を検証してください:
- Template: フィールドが小文字の "swell" になっているか（大文字不可）
- Theme Name が案件名と一致しているか
- Version が 1.0.0 から始まっているか

問題があれば修正した style.css を出力してください。
```

大文字・小文字の問題はLinuxサーバーへのデプロイ時に必ず問題になります。生成直後に確認する習慣をつけるため、このテンプレートをセットアップ後すぐに使います。

### カテゴリ2：動作確認・デバッグ

#### テンプレート2-A：PHPエラーの原因特定

WordPress管理画面やフロントエンドにエラーが出た場合の診断プロンプトです。

```
以下のPHPエラーが発生しています。原因と修正方法を教えてください。

【エラーメッセージ】
[エラーメッセージをそのままペースト]

【エラーが発生する状況】
- [例: テーマ有効化直後 / 特定のページを開いた時 / 管理画面カスタマイザーを開いた時]

【環境】
- WordPress [バージョン]
- SWELL [バージョン]（子テーマを使用）
- PHP [バージョン]
- [問題のファイル名]（該当ファイルのコードをコンテキストとして添付）

修正箇所のコードスニペットと、なぜその修正で直るのかの説明もあわせてください。
```

「なぜその修正で直るのか」を明示的に求めることがポイントです。修正コードだけ出してもらっても、次回同じ問題が出たときにまたClaudeに頼ることになります。理由を理解することで、自分でも判断できるようになります。

#### テンプレート2-B：デプロイ前コードレビュー

ローカル確認が完了して本番デプロイ前に実行するプロンプトです。

```
本番デプロイ前のコードレビューをお願いします。

【レビュー対象ファイル】
[ファイル内容をコンテキストとして添付、またはGitHubリポジトリのパスを指定]

【本番環境情報】
- サーバー: エックスサーバー
- PHPバージョン: [バージョン]（ローカルのMAMPは [バージョン]）
- WordPressバージョン: [バージョン]

以下の観点でレビューしてください:
1. 絶対パスのハードコードがないか（ローカル固有のパスが混入していないか）
2. PHPバージョン互換性（ローカルと本番のバージョン差異で動かないコードがないか）
3. WP_DEBUG=falseの本番でもエラーにならないか（Notice/Warningが潜んでいないか）
4. セキュリティ上の問題（nonce未検証、sanitize漏れなど）
5. SWELLのバージョン間差異で動かなくなる可能性のあるフック

問題があれば重大度（致命的/要対応/軽微）とともに列挙してください。
```

このテンプレートは「シリーズ前回」のデプロイ記事で紹介したワークフローをプロンプト化したものです。毎回同じ観点でレビューを依頼することで、見落としが減ります。

### カテゴリ3：機能追加・カスタマイズ

#### テンプレート3-A：カスタム投稿タイプの追加

```
既存のSWELL子テーマに、以下の仕様でカスタム投稿タイプを追加してください。

【追加する投稿タイプ】
- スラッグ: [英字スラッグ]
- 表示名（単数）: [日本語名]
- 表示名（複数）: [日本語名]
- 管理メニューアイコン: dashicons-[アイコン名]
- パブリック: true / false
- アーカイブページ: あり / なし
- カスタムフィールド: [フィールド名と型のリスト、またはなし]

【既存コード】
[inc/cpt-既存.php のコードをコンテキストとして添付]

以下の点を守って生成してください:
- 既存の投稿タイプのコードスタイルに合わせる
- 関数名プレフィックスは既存に合わせる（[プレフィックス]_）
- add_action の優先度は既存コードに合わせる
```

「既存コードのコンテキストを添付して既存コードのスタイルに合わせる」という指示が重要です。これがないと、既存コードと書き方が揃わず、後でメンテナンスしにくくなります。

#### テンプレート3-B：Contact Form 7のカスタマイズ

```
Contact Form 7 で以下のカスタマイズを実装してください。

【要件】
- [確認メールの送信元アドレスの設定]
- [確認メールの日本語文面テンプレート]
- [送信後のサンクスページへのリダイレクト]
- [スパム対策の追加（reCAPTCHA または Honeypot）]

【既存コード】
[inc/cf7-custom.php のコードをコンテキストとして添付]

【制約】
- CF7のバージョン: [バージョン]
- CF7のフォームタグは変更しない（フォーム設定画面での変更は不要）
- functions.phpへの追記ではなく、inc/cf7-custom.phpへの追記で実装する
```

CF7カスタマイズは「フォームタグを変更するか・PHPフックで実装するか」の切り分けが曖昧になりやすいです。「フォームタグは変更しない」と明示することで、管理画面のフォーム設定に手を加えないPHPのみの実装が得られます。

#### テンプレート4-A：案件別READMEの更新

```
以下の変更作業が完了しました。
READMEの「カスタマイズ一覧」セクションを更新してください。

【今回の変更内容】
- [変更1: 例「inc/cpt-works.php を新規追加、実績カスタム投稿タイプを実装」]
- [変更2: 例「inc/cf7-custom.php のメール文面を更新」]

【現在のREADME】
[README.mdの内容をコンテキストとして添付]

以下の形式でカスタマイズ一覧を更新してください:
| ファイル | 概要 | 更新日 |
|---|---|---|
既存行は変更せず、今回の変更を追記または既存行を更新してください。
```

#### テンプレート4-B：引き継ぎドキュメントの生成

副業案件では稀に「案件を他のエンジニアに引き継ぐ」場面が発生します。

```
以下のSWELL子テーマを他のエンジニアに引き継ぐための
ドキュメントを生成してください。

【コンテキスト】
[子テーマの全ファイルをコンテキストとして添付]

【引き継ぎ先エンジニアのスキル前提】
- WordPressの基本操作はできる
- SWELLの使用経験はない（または浅い）
- PHPの基礎知識はある

以下の項目を含めてください:
1. このテーマで行っているカスタマイズの一覧と目的
2. ローカル環境の立ち上げ手順（MAMP前提）
3. 各ファイルの役割と変更時の注意点
4. 本番デプロイ時のチェックリスト
5. よくあるトラブルとその対処法

Markdown形式で、HANDOVER.md として保存できる形式で出力してください。
```

### カテゴリ5：Claude Code自体の設定・最適化

#### テンプレート5-A：CLAUDE.mdの初期生成

```
このSWELL子テーマ開発プロジェクト用の CLAUDE.md を生成してください。

【プロジェクト情報】
- リポジトリ: [GitHubリポジトリのURL]
- メインの作業内容: WordPress/SWELL子テーマの開発・メンテナンス
- 使用するファイル構成: [ファイル構成の概要]

以下の内容を含めてください:
1. このリポジトリの概要（Claude Codeのセッション開始時に読まれる）
2. コーディング規約（PHPのスタイル、関数名プレフィックスのルールなど）
3. ファイル構成と各ファイルの役割
4. よく使うプロンプトパターンへの参照（「テンプレート集はZenn記事を参照」など）
5. 注意事項（やってはいけないこと、本番デプロイ時の確認事項など）

CLAUDE.md は次のセッション以降のClaudeが読んで理解できる形式にしてください。
```

CLAUDE.mdをClaudeに生成させる、という少し再帰的なアプローチですが、「Claude Codeのセッション開始時に読まれる」という目的を明示することで、適切なレベルの抽象度でドキュメントが作られます。

## ポイント

### 制約（constraint）を明示することが最重要

テンプレートの多くに「制約」セクションを設けています。「やりたいこと」だけを書いて「やってはいけないこと」を書かないと、Claudeは合理的な選択をしますが、それが自分の意図と異なる場合があります。

副業WordPress案件では特に「既存コードへの影響を最小化する」という制約が重要です。「追記のみで対応、既存コードは変更しない」と明示するだけで、不要な既存コードへの手戻りが大幅に減ります。

### コンテキストの質がアウトプットの質を決める

プロンプトに「関連ファイルをコンテキストとして添付」と書いていますが、どのファイルをコンテキストとして渡すかが重要です。

機能追加の依頼では、変更対象のファイルだけでなく「既存の似た実装を持つファイル」も渡すと、スタイルが統一された出力が得られます。たとえば「新しいカスタム投稿タイプの追加」では、既存の `inc/cpt-works.php` を一緒に渡すことで「このプロジェクトの書き方に合わせた」コードが生成されます。

### 「なぜ」を求める習慣がClaudeの誤りを減らす

エラーデバッグのテンプレートに「なぜその修正で直るのかの説明もあわせてください」という一文を入れています。これには2つの効果があります。

1つは自分の理解が深まること。もう1つは、Claudeの出力の検証ができること。「この修正で直る理由」の説明が論理的に正しければ修正が信頼できますが、説明が曖昧だったり理由がよくわからない場合は、修正自体が的外れである可能性があります。特にPHPのフックやWordPressのライフサイクルに関わる修正は、表面上は動いているように見えて別の副作用が出ることがあります。

### テンプレートはバージョン管理する

これらのプロンプトテンプレートは、案件をこなすたびに少しずつ改善されます。「このパラメータを追加したら出力がよくなった」「この制約を書かないとはまる」という知見が蓄積します。

テンプレートをMarkdownファイルとしてGitHubリポジトリに含めてバージョン管理しておくと、「以前はどんなプロンプトを使っていたか」が追えます。リポジトリ内の `prompts/` ディレクトリに場面別のテンプレートを置いて、CLAUDE.mdからリンクを張る構成が使いやすいです。

```
claudecode/
├── prompts/
│   ├── 01-setup.md        # セットアップ時のプロンプト
│   ├── 02-debug.md        # デバッグ時のプロンプト
│   ├── 03-customize.md    # カスタマイズ時のプロンプト
│   └── 04-handover.md     # 引き継ぎ時のプロンプト
└── CLAUDE.md              # 各テンプレートへの参照を含む
```

## まとめ

副業のWordPress/SWELL案件でClaude Codeを活用するための、場面別プロンプトテンプレートをまとめました。

| 場面 | 使うテンプレート | 主な効果 |
|---|---|---|
| 新規案件セットアップ | 1-A / 1-B | スタイル統一、環境差異の事前排除 |
| 動作確認・デバッグ | 2-A / 2-B | 原因特定の効率化、デプロイ前リスク低減 |
| 機能追加・カスタマイズ | 3-A / 3-B | 既存コードとの整合性維持 |
| ドキュメント・引き継ぎ | 4-A / 4-B | ナレッジの明文化・可搬性向上 |
| Claude Code設定最適化 | 5-A | セッション間の文脈引き継ぎ |

このシリーズ（SWELL子テーマ開発 × Claude Code）を通じて一貫してテーマにしてきたのは、**Claudeに「全部やらせる」のではなく、「自分が一番時間を取られている部分を肩代わりしてもらう」**という使い方です。

ローカルのWordPress操作は自分がやる。コードの方針判断も自分がやる。でも「ファイル生成」「デプロイ前チェックリストの網羅」「エラー原因の特定」「ドキュメント更新」といった、繰り返し発生してパターン化できる作業はClaudeに任せる。この分担が、副業案件のスループットを無理なく上げる現実的なアプローチです。

次回は、このプロンプトテンプレート集を**CLAUDE.mdとして整備してリポジトリに組み込み、毎回のセッション開始コストを下げる**仕組みの構築を予定しています。CLAUDE.mdにテンプレートへの参照を持たせ、「前回はどんなプロンプトで何を生成したか」をClaudeが自動で把握した状態でセッションを開始できる構成です。
