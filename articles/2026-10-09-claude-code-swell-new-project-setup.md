## はじめに

[前回の記事](https://zenn.dev/tomowingweb/articles/2026-10-02-claude-code-swell-child-theme-autodocs)では、Claude Codeのスケジュール実行でSWELL子テーマのPHPDocコメントを自動補完し、その内容をZenn記事のドラフトとして二重活用する仕組みを紹介しました。末尾で予告した通り、今回は**蓄積されたREADMEのカスタマイズ一覧を活用して、SWELL子テーマを新規案件に展開するセットアップ作業をClaudeで自動化する**実装を共有します。

副業でWordPress案件を複数抱えていると、「このフックは前の案件でも使ったな。確かあのリポジトリに実装があったはず…」という状況が頻繁に発生します。新規案件のたびに既存の子テーマを参照しながら、必要な部分をコピー&ペーストする作業は地味に時間を消費します。

今回は、数ヶ月かけて自動蓄積してきたREADMEのカスタマイズ一覧を「コンテキスト」としてClaudeに渡し、**新規案件の要件に応じて必要なカスタマイズを選定し、子テーマの初期ファイルセットを自動生成する**仕組みを構築しました。

## 環境

- WordPress + SWELL子テーマ（GitHub: `tomowingweb/claudecode`）
- Claude Code on the Web（Scheduled Tasks + 手動実行）
- Node.js 20.x / zenn-cli v0.5.x
- MAMP（ローカル開発環境）

## 課題：新規案件のたびに繰り返されるセットアップ作業

SWELL子テーマを複数案件で使っていると、初期セットアップで毎回発生する作業パターンがあります。

```
新規案件のセットアップ（毎回発生する作業）:
1. claudecodeリポジトリをクローン
2. README.mdのカスタマイズ一覧を眺める
3. 今回の案件に必要そうなフックを選ぶ（判断に10〜20分）
4. 選んだフックの実装を各PHPファイルからコピー
5. 新リポジトリに貼り付け、案件固有の設定に書き換え
6. functions.php でインクルード設定
```

この作業自体は難しくないのですが、特に**ステップ3の「どのフックを使うか選ぶ」判断**に時間がかかります。案件の要件（コーポレートサイト、ブログ、ECサイトなど）によって必要なカスタマイズが異なり、READMEを眺めながら「これは今回いるか？」を一つひとつ判断するのが手間です。

## 実装内容

### 全体アーキテクチャ

今回の仕組みは、スケジュール実行ではなく**手動トリガー型**です。新規案件を受注したタイミングで実行するコマンドを一本用意し、案件の概要を伝えるだけでセットアップ用ファイルを生成させます。

```
手動実行:
claude "新規案件: コーポレートサイト（会社概要・サービス・お知らせ）。
        カスタム投稿タイプ: works（実績）。
        問い合わせはContact Form 7。"
    │
    ▼
claudecodeリポジトリのREADME.mdを読み込む
    │
    ▼
カスタマイズ一覧から案件要件に合うものを選定
    │
    ▼
選定したカスタマイズのPHPファイルを読み込む
    │
    ▼
新規案件用ファイルセットを生成・出力
（functions.php / inc/ 以下のファイル群）
```

ポイントは**Claudeに選定の判断をさせる**ことです。どのフックが必要かの判断ロジックをプロンプトに記述することで、毎回の選定作業を省略できます。

### ステップ1：カスタマイズ一覧の読み込みと選定

まずClaudeに渡すプロンプトのコア部分です。

```markdown
## SWELL子テーマ新規案件セットアップ

### 案件概要
{ここに案件の概要を記述}

### 手順

1. `tomowingweb/claudecode` の README.md にある「カスタマイズ一覧」テーブルを読み込む
2. 案件概要と照合し、以下の基準で必要なカスタマイズを選定する：
   - **必須**：サイト種別（コーポレート/ブログ/EC）に共通して使うもの
   - **推奨**：案件概要に記載された機能に直接対応するもの
   - **不要**：案件概要に記載のない特殊機能（例：多言語対応、会員機能）
3. 選定結果をリスト形式で出力し、確認を待つ
```

このプロンプトを実行すると、Claudeはまず選定結果を提示して確認を求めます。例えばコーポレートサイトの案件では次のような出力が得られます。

```
【選定結果】

■ 必須（全案件共通）
- カスタム管理バー非表示 (inc/admin-ui.php)
- ログイン画面カスタマイズ (inc/login-custom.php)  
- ウィジェットエリア追加 (inc/widgets.php)

■ 推奨（今回の案件に合致）
- カスタム投稿タイプ「works」(inc/cpt-works.php)
  → 案件概要に「実績（works）」の記載あり
- Contact Form 7 確認メール日本語化 (inc/cf7-custom.php)
  → 「Contact Form 7を使用」の記載あり
- swell_head_description フィルター (inc/custom-hooks.php)
  → コーポレートサイトはSEO設定が重要なケースが多い

■ 今回は不要と判断
- 多言語対応ヘルパー (inc/i18n-helper.php)
  → 案件概要に多言語の記載なし

確認してよいですか？ (y/n)
```

この確認ステップを挟むことで、Claudeの判断ミスを人間がチェックできます。

### ステップ2：PHPファイルの生成

確認後、選定したカスタマイズのPHPファイルを読み込み、新規案件用にカスタマイズして出力します。

```markdown
## ファイル生成ルール

選定したカスタマイズのPHPファイルを読み込み、以下のルールで新規案件用ファイルを生成する：

### 変数・定数の書き換え
- プレフィックス `my_` は `{案件略称}_` に変更
  例：my_custom_meta_description → corp2026_custom_meta_description
- `CHILD_THEME_VERSION` の値は `1.0.0` にリセット

### コメントの整形
- PHPDocの `@since` は今日の日付に設定
- テンプレート元のリポジトリ名をコメントに残す
  例：`/* ported from tomowingweb/claudecode @2026-10-09 */`

### インクルード設定
- 生成したファイルをすべてインクルードする `functions.php` も出力する
```

生成されたファイルは、ディレクトリ構造を保ったままローカルに出力されます。

```
新規案件リポジトリ（生成後）:
├── functions.php          ← 自動生成（インクルード設定込み）
├── style.css
└── inc/
    ├── admin-ui.php       ← ported from claudecode
    ├── cf7-custom.php     ← ported from claudecode
    ├── cpt-works.php      ← ported from claudecode
    ├── custom-hooks.php   ← ported from claudecode
    ├── login-custom.php   ← ported from claudecode
    └── widgets.php        ← ported from claudecode
```

### ステップ3：案件固有のカスタマイズを追記

ポートしたファイルに加えて、案件概要から読み取れる**新規実装が必要なカスタマイズ**のスケルトンも生成します。

```markdown
## スケルトン生成ルール

案件概要を読み込み、既存のカスタマイズでは対応できない要件がある場合：
- `inc/project-specific.php` を新規作成する
- 実装が必要な関数のスケルトン（関数定義＋PHPDocのみ）を出力する
- 実装内容は空のまま残し、コメントで「TODO: 実装が必要」と明示する
```

これにより、既存の再利用部分と新規実装部分が明確に分離されます。

## ポイント

### READMEのカスタマイズ一覧が充実していることが前提

この仕組みの品質は、**README.mdのカスタマイズ一覧テーブルの完成度に直結します**。前回記事で自動更新してきたこの一覧が、今回の選定の判断材料になるため、記述が不正確だとClaudeの選定も不正確になります。

特に重要なのは「概要」列の記述です。「何をする」だけでなく「どんな案件で使う」という情報を一言添えると、Claudeの選定精度が上がります。

```markdown
| フック/関数 | ファイル | 概要 |
|---|---|---|
| cf7_confirm_mail_fix | inc/cf7-custom.php | CF7の確認メールを日本語化。CF7を使う全案件で必要 |
| swell_works_cpt | inc/cpt-works.php | 実績（works）カスタム投稿タイプ。制作会社・個人事業主案件向け |
```

「CF7を使う全案件で必要」「制作会社・個人事業主案件向け」という記述が、Claudeの選定判断のヒントになります。

### プレフィックスの命名ルール

生成ファイルでの関数名プレフィックスは、案件ごとに固有のものを使います。コーポレートサイトなら `corp2026_`、ブログなら `blog_` といった具合です。

これにより、複数の子テーマを同一WordPress環境に入れてテストする際の関数名衝突を防げます。副業で複数案件のローカル環境を一つのMAMPで管理している場合、この問題は意外と頻繁に発生します。

### 「porting」の記録を残す意義

生成ファイルにポート元のリポジトリ名と日付を残す（`/* ported from tomowingweb/claudecode @2026-10-09 */`）ことには、後からの保守で大きな意味があります。

元リポジトリ側でバグが見つかって修正した場合、このコメントがあれば「どの案件リポジトリに同じバグがあるか」をgrepで追跡できます。自動化のスケール感が増すほど、このトレーサビリティが重要になります。

## まとめ

蓄積したSWELL子テーマのREADMEカスタマイズ一覧をコンテキストとして使い、Claude Codeに新規案件のセットアップを自動化させる仕組みを構築しました。

| 作業 | 自動化前 | 自動化後 |
|---|---|---|
| カスタマイズ選定 | 20〜30分（READMEを眺めて判断） | Claudeが案件要件から自動選定（確認のみ） |
| ファイルコピー&ペースト | 15〜20分（ファイルを探してコピー） | 自動生成（プレフィックス書き換え込み） |
| functions.phpの設定 | 10分（インクルード設定） | 自動生成 |
| 新規実装のスケルトン作成 | 手動（都度作成） | 案件概要から自動生成 |

この仕組みは、**自動ドキュメント更新（前回記事）があって初めて成立する**点が重要です。READMEが充実しているほど選定の品質が上がり、選定の品質が上がるほどセットアップの効率が上がる、という正のフィードバックが働きます。

次回は、この新規案件セットアップの仕組みをさらに一歩進めて、**生成した子テーマファイルの初期動作確認をClaudeと一緒に行うワークフロー**を試みる予定です。MAMPのローカル環境へのデプロイからWordPress管理画面での確認まで、Claude Codeをセットアップ作業のペアプログラマーとして活用する方法を探ります。
