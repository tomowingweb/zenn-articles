## はじめに

[前回の記事](https://zenn.dev/tomowingweb/articles/2026-09-25-claude-code-zenn-series-aware-drafts)では、Claude Codeのスケジュール実行による記事ドラフト生成を「連載対応」にアップグレードし、過去記事を参照して重複を避ける仕組みを整えました。末尾で予告した通り、今回は **SWELL子テーマのソースコードコメントとREADMEをClaudeに自動更新させ、その更新内容をそのままZenn記事のネタとして使う「二重活用」の仕組み** を試みます。

副業のWordPress案件でSWELL子テーマを育てていると、コードは日々変わるのにドキュメントが追いつかない、という状況がしばしば発生します。「このフックは何のためにあるんだっけ？」と自分で書いたコードを見て首をかしげる、あの感覚です。

一方でZennへの技術アウトプットも続けたい。この二つの課題を同時に解決できないかと考えた結果、「**Claude Codeにコードを読ませてドキュメントを更新させ、何をどう変えたかをZenn記事のドラフトに書かせる**」という流れを作ることにしました。

## 環境

- WordPress + SWELL子テーマ（GitHub: `tomowingweb/claudecode`）
- Claude Code on the Web（Scheduled Tasks）
- Node.js 20.x / zenn-cli v0.5.x
- GitHub（`tomowingweb/zenn-articles`）

## 課題：コードとドキュメントの乖離

SWELL子テーマの開発を1年以上続けていると、`functions.php` や `inc/` 以下のファイルに様々なカスタムフックやショートコードが蓄積されていきます。

典型的な問題パターンがいくつかあります。

```php
// inc/custom-hooks.php の一部（ドキュメントがない例）
add_filter( 'swell_head_description', 'my_custom_meta_description', 10, 2 );
function my_custom_meta_description( $desc, $post_id ) {
    // なぜこの処理が必要なのか、もはや自分でも覚えていない
    if ( is_singular( 'works' ) ) {
        $custom = get_post_meta( $post_id, '_custom_description', true );
        return $custom ? $custom : $desc;
    }
    return $desc;
}
```

このようなコードが増えると、半年後の自分（あるいは引き継ぎ先）が困ります。かといって毎回コメントを丁寧に書く時間は、副業案件の合間にはなかなか取れません。

## 実装内容

### 全体のアーキテクチャ

今回構築した仕組みの全体像です。

```
毎週木曜 深夜（JST）
    │
    ▼
Scheduled Tasks が起動（zenn-articles セッション）
    │
    ▼
claudecode リポジトリの直近コミットを確認
    │
    ▼
変更されたPHPファイルのコードコメントをClaudeが補完・更新
（claudecode リポジトリへコミット）
    │
    ▼
「何を・なぜ更新したか」をZenn記事ドラフトに記述
（zenn-articles リポジトリへコミット）
```

ポイントは、**一度のセッションで2つのリポジトリを操作する**ことです。コードのドキュメント更新とZenn記事生成を同一セッション内で完結させることで、「コードを更新したらドキュメントが自動でできていて、記事の下書きまで出来上がっている」という状態を作れます。

### ステップ1：変更ファイルの特定とコメント補完

スケジュールタスクのプロンプトに、以下の手順を追加しました。

```markdown
### ドキュメント更新ステップ（追加）

1. `tomowingweb/claudecode` の直近7日のコミットで変更されたPHPファイルを特定する
2. 変更ファイルを読み込み、コメントが不足している関数・フックを特定する
3. 以下の基準でコメントを追加・更新する：
   - 各関数の先頭に「何をする関数か（1行）」「なぜ必要か（背景）」を追記
   - add_filter/add_actionには「どのSWELLフックへの介入か」を記載
   - 引数の型と意味を @param で記載（WordPress Coding Standards準拠）
4. 更新したファイルをclaudecodeリポジトリにコミットする
   コミットメッセージ形式: `docs: [ファイル名] PHPDocコメントを補完`
```

Claude Codeはこの指示に従い、例えば先ほどのコードを以下のように補完します。

```php
/**
 * カスタム投稿タイプ「works」の meta description をカスタムフィールドから上書きする。
 *
 * SWELL標準の swell_head_description フィルターを利用して、
 * 投稿編集画面で設定した `_custom_description` カスタムフィールドの値を
 * meta description として出力する。フィールドが空の場合はSWELL標準の値を使用。
 *
 * @param string $desc    SWELL が生成したデフォルトの meta description
 * @param int    $post_id 現在の投稿ID
 * @return string 最終的に出力する meta description
 */
add_filter( 'swell_head_description', 'my_custom_meta_description', 10, 2 );
function my_custom_meta_description( $desc, $post_id ) {
    if ( is_singular( 'works' ) ) {
        $custom = get_post_meta( $post_id, '_custom_description', true );
        return $custom ? $custom : $desc;
    }
    return $desc;
}
```

コードの意味がコンテキストから明確に読み取れるため、Claudeはかなり正確にコメントを書いてくれます。

### ステップ2：README.mdへの「更新ログ」追記

PHPDocコメントだけでなく、リポジトリのREADME.mdにある「カスタマイズ一覧」セクションも自動更新します。

```markdown
### README更新ステップ（追加）

claudecodeリポジトリの README.md に「カスタマイズ一覧」セクションがない場合は作成し、
ある場合は今週の変更内容を追記する。

形式：
| フックまたは関数 | ファイル | 概要 |
|---|---|---|
| `swell_head_description` | inc/custom-hooks.php | worksのmeta descriptionをカスタムフィールドから設定 |
```

このテーブルは週次で蓄積されていくため、数ヶ月後には「このリポジトリで何ができるか」が一覧で把握できるリファレンスになります。

### ステップ3：Zenn記事ドラフトへの転用

コードのドキュメント更新が完了した後、同じセッションでZenn記事のドラフトを生成します。

このステップで重要なのは、**ドキュメント更新の過程で得た「なぜこのコードがあるのか」という情報を記事に活かす**ことです。

プロンプトの指示：

```markdown
### Zenn記事ドラフト生成（ドキュメント更新後に実行）

上記のドキュメント更新で把握した内容を元に、Zenn記事のドラフトを生成する。

記事の「実装内容」セクションでは：
- 今週追加・変更したフックや関数の具体的なコードを掲載する
- 「なぜこの実装が必要だったか」という背景を記述する（PHPDocの背景説明を転用してよい）
- 実際のサイトでの動作の変化（Before/After）を記載する

「ポイント」セクションでは：
- SWELL固有のフック名や動作仕様で注意すべき点を記載する
- 同様の実装をする開発者が詰まりやすいポイントを書く
```

PHPDocとZenn記事は同じ情報をターゲット読者に合わせて書き直したものなので、Claudeにとっても一貫した情報源から記述できます。

## ポイント

### PHPDocの品質コントロール

自動生成されたコメントをそのままマージするのは少し怖い、という場合のために、プロンプトに以下の制約を設けています。

- **既存のコメントは上書きしない**：コメントがすでに存在する関数は変更しない
- **コード本体は一切変更しない**：コメント追加のみ許可
- **PRは作成せずコミットする**：自分でdiffを確認してからマージする運用を維持

3つ目のルールについて補足すると、`claudecode` リポジトリへの直接プッシュはせず、一度ブランチにコミットしてPRを作成する方針も考えました。ただし毎週差分が小さい場合はオーバーエンジニアリングになるため、現状はmainブランチへの直コミットで運用し、コメントの品質に問題があれば都度修正しています。

### SWELL固有フックの正確な記述

SWELLのカスタムフックは公式ドキュメントに全てが掲載されているわけではなく、ソースコードや公式サポートコミュニティを参照しないと正確な動作がわからないものがあります。

Claudeはコードの文脈からフックの動作を推測しますが、SWELL固有の挙動（例：カスタマイザーとの連携、モバイル/PCの出し分け）については誤った説明を生成することがあります。

対策として、プロンプトに以下を追加しました。

```markdown
SWELLのフック名に関するコメントを書く場合：
- フックの第一引数・第二引数の型と意味は、コード内の実装から推測して記述する
- 「SWELLのXX機能に対応するフック」という断言はしない
  → 代わりに「おそらく〜に対応（要確認）」とメモとして残す
```

「要確認」コメントが残ったものは、自分で公式サポートに問い合わせるか、実際の動作を確認して修正します。完全自動化よりも「大部分は自動化、残り5%は人間が確認」という運用が現実的です。

### 記事と実装の「鮮度」が一致する

この仕組みの副次的な利点として、**記事に書くコードが必ず「今週実際に書いたコード」になる**という点があります。

過去に記事を手動で書いていたころは、実装から数週間後に記事を書くため「コードは正しいが細部の記憶があいまい」な状態になりがちでした。自動化後は実装直後にドキュメントが生成されるため、コードの意図が記事にリアルタイムで反映されます。

## まとめ

Claude Codeのスケジュール実行を使って、SWELL子テーマのPHPDocコメント自動補完とZenn記事ドラフト生成を一つのセッションで実現しました。

| 作業 | 自動化前 | 自動化後 |
|---|---|---|
| PHPDocコメント追記 | 毎回手動（後回しにしがち） | 変更ファイルを自動検出して補完 |
| README更新 | 月1回まとめて更新（漏れる） | 週次で自動追記 |
| Zenn記事のネタ探し | コミット振り返りに30分 | ドキュメント更新の副産物として取得 |
| 記事ドラフトの「実装内容」 | 60〜90分（コードを見ながら説明文を書く） | PHPDocを元に自動生成 |

この仕組みの本質は「Claudeへの説明（PHPDoc）とZennの読者への説明（記事）が同じ情報を共有している」という点です。一方を改善するともう一方の品質も上がる、という正のフィードバックが働きます。

次回は、蓄積したREADMEのカスタマイズ一覧を活用して、**SWELL子テーマをテンプレートとして他案件に展開するときのClaudeを使ったセットアップ自動化**を試みる予定です。「このフックは毎回使うから新規案件でも最初から入れる」という判断を、蓄積されたドキュメントからClaudeに自動化させます。
